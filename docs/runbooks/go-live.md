# Go-live runbook (one runbook for the whole product)

Written 2026-10-01 for Task 27 (prep). Nothing in this file has been run against production. It was written from the sources named on each line, with the local tools only. Every command here is for go-live day.

## How to read this

Every line has an id, a type, a pass condition and a "stop if" condition.

- SCRIPT: runs locally on the user's machine, needs no account (a SCRIPT tagged `spends money` calls a model provider with the user's own keys).
- PROBE: an exact command run against production at go-live. Read-only unless the line is tagged `changes production`: every PROBE (or MANUAL then PROBE) line that writes to production D1, R2 or a mailbox carries that tag, and its command names the one site and owner it may touch. A line whose result is a recorded observation still gives the exact command that produces it.
- MANUAL: an account, dashboard or device step.

"SRC" names where the line comes from: `T27c #N` is item N of `.superpowers/sdd/task-27-checklist.md` (kept in the Plan 4 lane A folder), `P4 T27 S<n>` is a step of Task 27 in `docs/superpowers/plans/2026-09-24-plan4-app.md` (:15843), `P2 T19 S<n>` is a step of Task 19 in `docs/superpowers/plans/2026-09-24-plan2-hosting-publish.md` (:7685), `P3 H` is `docs/superpowers/handoffs/plan3.md`, `P3 T15 S<n>` is Task 15 of `docs/superpowers/plans/2026-09-24-plan3-generation.md` (:5107), and `A16 H` is `.superpowers/sdd/a16-handoff-plan4.md`.

Code of the A16 pointer model is read with `git show 50cb3cb:<path>`. Commit 50cb3cb (branch plan-a16-pages) is not on the Plan 4 branches yet. Once A16 is on main, re-check every `50cb3cb:` line number with `git grep -n` before trusting it. A line that says NEEDS DECISION has a source that is ambiguous or silent: the decision belongs to the moderator or the user, and nobody guesses.

### 5.3 The deploy order (derived from the code)

The rule: a Worker that READS keys is deployed AFTER the Worker that WRITES them, so a new reader never meets keys an old writer never wrote. The chain in the A16 code:

1. The app WRITES the stored pages: `createPendingVersion` puts one WORK object per page and writes `pages_json` and the digest `html_sha256` (`50cb3cb:packages/publishing/src/versions.ts:69-92`). The app Worker is the caller of `createPendingVersion` (`apps/app/src/worker/deps.ts:53`).
2. The admin READS those pages (`verifiedPages`, `50cb3cb:packages/publishing/src/shared.ts:62-82`, called from `review.ts:55`) and WRITES the LIVE pages and the POINTER (`copyLivePages` `review.ts:57`, `writeLivePointer` `review.ts:77`; restore and takedown in `site-state.ts`).
3. The sites Worker READS the POINTER first and then the page key it names (`50cb3cb:apps/sites/src/page.ts:24-29, 36, 45`).

So the order is: migrations, generator, app, admin, sites. The generator is independent of the pointer (it consumes the generation queue and writes D1 `generations`), so it goes first; it does nothing while `GENERATION_ENABLED` is `"false"`.

What visitors and admins see at each step, with the preconditions of G5.3 met (no live site, no pending version):
- After migrations: nothing changes (old code ignores `pages_json`).
- After the generator: nothing public.
- After the app (new): owners can request publication; each request stores pages. Visitors: no site is live, every host answers the plain 404 page. The old admin, if one runs, cannot approve such a version: `html_sha256` is now a digest, not the hash of the Home bytes, so the check fails with an integrity error (it fails closed, never publishes). Rule R1: nobody approves anything in this window; the admin queue stays untouched until the admin is deployed.
- After the admin (new): approve, restore and take down now work on the pointer model. The old sites Worker, if one still runs, reads `<slug>.html` and never sees a pointer: a site approved now would answer 404 there (and a site approved twice would answer 503: its `<slug>.html` names an older version than D1's live version, `HEAD:apps/sites/src/page.ts:39`). Rule R2: nobody approves, restores or takes down a site between the admin deploy and the sites deploy. This is minutes; with no live site there is nothing to take down.
- After the sites Worker (new): a site with no pointer answers 404 on every page ("Page not found"). The first approval of each site (or a restore, which rewrites the pointer) writes it. That is the transitional rule: a site becomes visible only when it has been approved once on the new code. For the first go-live this is just the first approval (the smoke-test site of section 7 does it).

PASS (whole section): the order was followed and R1 and R2 held.
